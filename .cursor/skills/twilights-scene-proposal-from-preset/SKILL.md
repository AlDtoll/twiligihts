# Twilights — предложение сцены из пресета

## Когда применять

Применяй этот skill, когда пользователь просит сделать предложения/техдок сцены на основе:

- `*_preset.md`
- `*_character.md`
- примеров существующих сцен (`*_design_proposal.md`, `*.md`, `*_player.md`)

Особенно если пользователь явно упоминает `PROJECT_CONTEXT` и `SCENE_CREATION_GUIDE`.

## Обязательные источники (прочитать в начале)

1. `PROJECT_CONTEXT.md` (корень репозитория).
2. `SCENE_CREATION_GUIDE.md` (читать секциями, не грузить целиком без нужды).
3. Целевые файлы пресета и персонажа, указанные пользователем.
4. Минимум 1-2 референса похожих сцен из `example/`.

## Workflow

1. **Собрать вводные**
    - Извлечь из пресета: замысел, цель сцены, желаемые механики, ограничения.
    - Извлечь из character-файла: мотивацию, тон, конфликт персонажа.

2. **Синхронизировать с движком**
    - Проверить, что предложения выражаются через поддерживаемые сущности Twilights:
      `hero`, `enemy`, `settings`, `heroRules`, `statuses`, `conditions`, `effects`, `stocks`.
    - Не придумывать механики, которых нет в формате сцены.

3. **Собрать каркас предложения**
    - Роль игрока и фокус сцены.
    - Смысл HP героя/противника.
    - 5 типов очков (gemType 1-5) и их роли.
    - Руки героя и логика противника.
    - Угрозы/эскалация/реакции.
    - Условия завершения и вариативные исходы.

4. **Локации и перемещение (если релевантно)**
    - Если сцена про исследование, предложить локации через статусы.
    - При частом перемещении добавлять мягкую санкцию темпа (дебаф на ход, срез накопления, рост
      риска).

5. **Финализация**
    - Выдать практичный техдок-предложение, которое можно напрямую переводить в `_base.json`.
    - Для `_base.json` рекомендовать схему `conditionDefs` / `effectDefs` / `statusDefs` с короткими
      ссылками на повторяемые блоки и дальнейшим раскрытием через `scripts/expand_scene.py`.
    - По запросу пользователя сразу создать `.md` файл рядом со сценой.

## Важные правила качества

- Не фиксируй "единственную истинную причину" заранее, если пользователь хочет, чтобы версия
  формировалась действиями игрока.
- Если у пользователя явный запрос на "игрок всегда прав", проектируй ветки так, чтобы выбранная
  линия расследования подтверждалась по мере прохождения.
- Плохие исходы телеграфировать заранее; не делать внезапный критический провал без окна на реакцию.
- Детективные действия можно делать с низкой/нулевой ценой, но компенсировать вероятностями,
  условиями, риском и контекстом локации.
- В `HeroStatuses` и `EnemyStatuses` не объявляй заранее служебные/ветвящиеся статусы с `value: 0`.
  Такие статусы должны появляться только в момент первого применения через `EDIT_STATUS`
  (`SET`/`CHANGE`). Исключение — если в сцене осознанно нужен стартовый статус с положительным или
  отрицательным значением.

## Шаблон результата

Используй структуру:

1. Роль игрока и фокус сцены
2. Главная рамка выбора/исследования
3. HP и темп сцены
4. Типы очков (1-5)
5. Локации и перемещение
6. Руки героя (по gemType)
7. Противник/среда угроз
8. Финалы
9. Что сразу вынести в `_base.json` (`statusDefs`, `conditionDefs`, `effectDefs`)

## Выходные артефакты

- По умолчанию: текст предложений в ответе.
- Если пользователь просит "зафиксировать": создать файл
  `<scene>_design_proposal.md` в директории сцены.
